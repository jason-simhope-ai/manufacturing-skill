# 確效與變更管制

> ⚠️ **Alpha**：本文是 agent 操作參考用的導讀，**不取代確效主計畫（VMP）、公司程序書與法規原文**。所有天數、批數、分級、驗收標準都是 **範例**，標「需驗證」處以主管機關現行公告與貴公司程序為準。

由 **deviation-capa-coordinator** 與 **batch-record-reviewer** 使用（CAPA 是否觸發變更 / 再確效、設備 / 系統確效狀態是否有效）。

---

## 名詞：確認（Qualification）vs 確效（Validation）

| 對象                     | 用語                 | 證明什麼                                           |
| ------------------------ | -------------------- | -------------------------------------------------- |
| 設備、設施、公用系統     | 確認（DQ/IQ/OQ/PQ）  | 設計對、裝對、照規格運轉、在實際條件下穩定表現     |
| 製程                     | 製程確效（PV）       | 製程能穩定產出符合品質的產品                       |
| 清潔                     | 清潔確效             | 清潔後殘留（活性成分、清潔劑、微生物）低於限量     |
| 分析方法                 | 方法確效             | 方法適合其用途（專一性、準確度、精密度…）          |
| 電腦化系統               | 電腦化系統確效（CSV） | 系統符合預期用途、資料完整性受控                  |

## 設備確認：DQ → IQ → OQ → PQ

| 階段 | 問題                         | 範例內容（以 V 型模型對應 URS）                         |
| ---- | ---------------------------- | ------------------------------------------------------- |
| URS  | 我們需要什麼？               | 使用者需求規格：產能、材質、清潔性、資料紀錄需求       |
| DQ   | 設計能滿足 URS 嗎？          | 設計審查、供應商文件、GMP 符合性                        |
| IQ   | 裝對了嗎？                   | 型號 / 序號、公用系統接點、圖面、校正、文件、軟體版本   |
| OQ   | 在操作範圍內照規格運轉嗎？   | 各參數上下限、警報、互鎖、斷電復歸                      |
| PQ   | 實際條件下長期穩定嗎？       | 用實際產品 / 模擬物、連續數次（次數範例，依風險定）     |

每份 protocol **先核准再執行**；執行中的偏離走偏差；最後有核准的報告才算完成。

## 製程確效生命週期（FDA 2011 三階段，PIC/S Annex 15 概念相近）

1. **製程設計** — 從開發知識定出關鍵製程參數（CPP）與關鍵品質屬性（CQA）
2. **製程性能確認（PPQ）** — 以商業規模證明製程可重現（批數依風險與科學理由定，不是固定「三批」— 需驗證你的主管機關期待）
3. **持續製程確認（CPV）** — 量產後持續監控趨勢（可搭配 core [`spc-basics`](../../../core/skills/spc-basics.md)）

## 電腦化系統確效（CSV）

- **風險導向**：依系統對病患安全、產品品質、資料完整性的影響決定確效深度（GAMP 5 的軟體分類與風險方法為業界常見參考，版次需驗證）
- 關鍵要素：預期用途 / URS、供應商評估、組態與測試、權限、audit trail、電子簽章、備份還原、定期審查、變更管制
- 美國 FDA 另有 CSA（Computer Software Assurance）思路，強調以批判性思考取代過度文件化（適用範圍與現行狀態需驗證）

### AI 工具本身也是電腦化系統

在 GxP 範圍內使用 AI（包括本 plugin）前，需由貴公司界定**預期用途**並評估是否需確效。**本 plugin 未經確效**；因此它的輸出不能成為 GMP 紀錄，只能是由人審核後重新產出的參考草稿。建議先用於非 GxP 範圍（教育訓練、草稿、整理公開資料）。

## 變更管制流程

對應 core [`engineering-change-process`](../../../core/skills/engineering-change-process.md) 的 5 步驟，GMP 版加上**法規影響**與**確效影響**：

```
1 變更申請   → 編號、說明 Before / After、理由
2 分類       → Minor / Major / Critical（依程序書，範例）
3 影響評估   → 品質、確效、法規申報、文件、訓練、供應商、庫存 / 在製品、穩定性
              ※ 以 ICH Q9(R1) 風險評估支持
4 QA 核准    → 含實施前需完成的條件（例如確效、法規核准）
5 實施       → 文件改版生效、訓練完成、系統組態更新
6 驗證與結案 → 確認實施完成、效果符合預期（有效性確認），QA 結案
```

**法規申報影響**由法規事務（RA）判定：台灣藥品 / 醫材許可變更（變更登記類型需驗證）、美國藥品的 PAS / CBE-30 / CBE-0 / 年報分類（21 CFR 314.70，需驗證）。**AI 不決定變更類別、不決定是否申報。**

常見缺失：先改後補單；只看文件沒看確效；忘了供應商通知；變更已核准但實施條件（如再確認）未完成就開始生產。

## 什麼時候要再確效 / 再確認（觸發條件）

| 觸發                                         | 常見需評估的項目（範例）                    |
| -------------------------------------------- | ------------------------------------------- |
| 設備主要零件更換、移機、改造                 | IQ / OQ 部分或全部、PQ                      |
| 製程參數範圍、批量規模、製程步驟變更         | 製程確效（PPQ）、穩定性                     |
| 關鍵原料 / 包材換供應商或規格                | 製程確效影響評估、穩定性、清潔確效          |
| 新產品導入共用設備                           | 清潔確效最差情況重新評估                    |
| 電腦化系統升級、組態或介面變更               | 回歸測試範圍依風險                          |
| 定期審查（periodic review）發現漂移          | 依結果決定                                  |
| 偏差 / OOS / 投訴趨勢顯示製程能力下降        | CAPA → 可能觸發再確效                       |
| 分析方法變更或移轉到其他實驗室               | 方法確效 / 移轉                             |

> 不是每個變更都要「全套重做」— 用風險評估決定範圍，並把理由寫進變更單。**結論由確效負責人與 QA 核准。**

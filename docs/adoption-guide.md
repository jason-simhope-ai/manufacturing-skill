> 給「拿這個 plugin 去客戶端導入」的人看。
> 包括 Jason 自己對外當顧問時用的 SOP。

## 適用對象

- 製造業內部 IT / AI 專案負責人
- 外部 AI 導入 SI / 顧問
- 製造業老闆 / 接班人想自己導入

## 標準導入順序（建議 6 週）

> 這是 agent／MCP 的導入順序（W0–W6），**不是分身 pilot**。分身 pilot 是 **4 週**（第 1 週模擬預演、第 2–4 週測試工作區），見下方「導入分身團隊的順序」一節；董事長要簽的三件事（原則、pilot 核准、預算核准）整理在[董事長一頁](owner-one-page.zh-TW.md)。

```
W0 (週 0)：先決定要不要做
  ├─ 跑 self-assessment（下方）
  └─ 老闆 + IT 主管 alignment

W1：硬體 + 環境
  ├─ 採購 GB10（or 替代硬體）
  ├─ Ubuntu / DGX OS 裝好
  ├─ 裝 Ollama + 下載模型
  └─ 裝 Claude Code（如還沒有）

W2：plugin 安裝 + smoke test
  ├─ git clone + bash install.sh
  ├─ 測 /quote /order-status 是否有反應
  ├─ 跑 examples/ 的 demo
  └─ 業助 / 廠長 各 1 人用 1 天

W3：profile 客製
  ├─ 找 1-2 個跟 CNC profile 不太一樣的地方（材料庫、機台、流程）
  ├─ 開 profile fork：profiles/<your-company>-cnc/
  ├─ 改 agents 內的 prompt（公司術語、客戶名）
  └─ 改 know-how 內的 SOP（公司專屬）

W4：MCP 接資料
  ├─ manufacturing-scheduler（infra/mcp-servers/scheduler-mcp）接你的 MES / 排程系統：把 `infra/mcp-servers/scheduler-mcp/mock-data/`
  │    （示範用的負載與工單）換成你 MES 的資料來源；未接上前，所有狀態類輸出都會標示「模擬資料」
  ├─ erp-connector 接你的 ERP（最花時間，常 1-2 週）：**不是換 mock data**，
  │    而是自己實作一個符合 `infra/mcp-servers/erp-connector/contract.py` 的連接器
  │    ├─ 讀取：走唯讀 view 或唯讀 replica，使用唯讀服務帳號
  │    └─ 寫入：只能走 ERP 官方 API，使用另一組只給連接器的服務帳號，不得直寫資料庫
  └─ 註冊 MCP server：plugin 安裝程式**不會**佈署 `infra/`，也不會註冊 MCP server。
       請用 `claude mcp add` 另外註冊，指令請用 server 的絕對路徑，例如
       `claude mcp add manufacturing-scheduler -s project -- python3 /abs/path/to/infra/mcp-servers/scheduler-mcp/server.py`
       （`-s local` 預設只對註冊時的那個資料夾有效；`-s project` 產生 `.mcp.json` 供團隊共用、成員須核准；
       `-s user` 對這個使用者的所有專案有效。確切選項以 `claude mcp add --help` 為準）

W5：使用者試跑
  ├─ 業助試報價（同時人工跑一次對照）
  ├─ 廠長查狀態（驗證 scheduler MCP 對得上）
  ├─ 品管試 /inspect（驗證 IATF 規範對齊）
  └─ 收集回饋、調 prompt

W6：上線 + 文件
  ├─ explainer 圖卡印 A3 掛到對應部門
  ├─ 培訓 30 分鐘（每個部門）
  ├─ 第一個月密集 review，每週調整
  └─ 設置 office hour（IT 答疑）
```

## W0 Self-Assessment（評估能不能做 / 該不該做）

### Pre-flight checklist

- [ ] **公司有 Claude Code 帳號 OR 有預算買** — plugin 是 Claude Code plugin
- [ ] **IT 部門能配合** — 至少 1 人懂 bash、能裝 Ubuntu 軟體
- [ ] **有 ERP / MES** — 不然 agent 沒資料可查；如果完全沒有，先做地端「假 ERP」用 SQLite
- [ ] **流程已經數位化** — 報價、工單、檢驗都還在紙本？先做基本數位化
- [ ] **老闆理解這是輔助、不是取代人** — 預期管理對齊
- [ ] **有 1-2 個願意試的「種子使用者」** — 通常是 30-40 歲、會用智慧型手機、願意給回饋的業助 / 工程師

### Red flags（不適合導入）

- ❌ 老闆覺得「裝了就裁員」 → 內部反彈會讓你失敗
- ❌ IT 部門完全外包、自己沒人 → 維運接不住
- ❌ 完全紙本流程 → 應該先做數位轉型再來導 AI
- ❌ 客戶完全不在乎稽核 / 文件 → AI 帶來的合規優勢無從發揮
- ❌ 預算 < NT$50K → 連 GB10 都買不起，建議先用雲端 + 非敏感資料試跑

## W3 客製化 — 最常見的 5 個改動

導入時 90% 客戶會要求改這 5 個地方：

### 1. 公司術語

`core/agents/*.md` 內把「機台」改成你工廠的稱呼（如「車台」、「銑台」）。

### 2. 客戶分級

`erp-connector` 接到客戶分級後，調整 `quote-specialist` 的利潤率邏輯。

### 3. 機台費率、毛利、料價

機台費率、毛利帶、風險加成、標準料價**沒有放在 scheduler 的 mock data 裡**。
`infra/mcp-servers/scheduler-mcp/mock-data/machine_loads.json` 只是機台「負載」的示範資料，不含費率。
機台費率在 ERP 端（`ErpConnector.get_machine_rate`，見 `infra/mcp-servers/erp-connector/contract.py`）；
連接器範例實作的 mock 若存在，費率放在 `infra/mcp-servers/erp-connector/mock-data/erp_mock.json` 的 `machine_rates`
（此檔隨 ERP 連接器範例實作提供，clone 裡沒有該檔就代表尚未包含該實作）。
請改為填寫 [`examples/company-facts.template.md`](../examples/company-facts.template.md)（見下一節），
存成 `company-facts.md` 放在 repo 之外，報價時用 `@` 附上。

### 4. 標準件庫

如果有公司專用的標準件庫（夾治具、刀具、模治具），加到 `core/know-how/<company>-standard-parts.md`（或你的 profile 下的 `know-how/`）。

### 5. 報價單版面

`examples/sample-quote-output.md` 改成你公司的版面（含公司 logo、條款、銀行資訊）。

## 公司事實檔（company-facts）與真實資料存放

### 用 company-facts 讓 agent 用你的數字

1. 複製 [`examples/company-facts.template.md`](../examples/company-facts.template.md) 為 `company-facts.md`。
2. 填入機台費率、毛利帶、風險加成、料價、交期常規、核准權限與資料分類規則。範本內所有數字都是「範例」佔位值，須全部換成自己的。
3. 沒把握的欄位留空或寫「待確認」，讓 agent 標成 `[ASSUMED]` 再由人確認。
4. 使用時明確附上，例如 `/quote @~/factory-work/rfq/客戶A-RFQ.pdf @~/factory-work/company-facts.md`。目前不要假設 agent 會自動讀到這個檔案。
5. 此檔通常屬 T2 機密（含費率與毛利），分級見 [docs/data-classification.md](data-classification.md)。

### 真實資料放哪裡

**原則：真實資料放在 repo 之外的工作資料夾**，例如 `~/factory-work/`，底下自行分 `customer-data/`、`drawings/`、`rfq/`、`logs/`。
在那個資料夾裡開 Claude Code，而不是在本 repo 的 clone 裡操作。

`.gitignore` 另外提供一道保險：若你不小心在 repo 內建立 `company-facts.md`、`customer-data/`、`drawings/`、`rfq/`、`logs/`，
或放入 `*.dwg`、`*.step`、`*.stp`、`*.iges`，它們不會出現在 `git status`。`examples/` 底下的合成資料仍照常追蹤。
這只防止誤 commit，**不代表資料沒有被送到 AI 服務**；哪些資料能送去哪裡，以資料分級為準。

### 未接 ERP / MES 時

沒有 MCP 連線時，`/order-status`、`/morning-briefing` 等指令只會用 mock data 回答，並須標示「模擬資料」；
不要把這些輸出當成真實訂單狀態或機台負載。

| 雷                 | 為什麼會踩              | 對策                                           |

## 導入分身團隊的順序（v0.2.0-alpha，實驗性）

> 這一節只談「虛實整合團隊」（每個職位一個副駕分身）。分身層不依賴 W1–W6 的 GB10 與 MCP 整合；最小前置條件是 [team/README.zh-TW.md](../team/README.zh-TW.md) 開頭「誰不該現在導入」的六件事（Slack 或 Discord 工作區、一台常駐主機與一位金鑰保管人、至少兩位每週 15 分鐘的主管、資料已數位化且能去識別成 T1、公司接受 T1 內容送雲端模型、「AI 賦能原則」已簽署）。董事長要簽的三件事（原則、pilot 核准、預算核准）與費用、停機、第 4 週怎麼判，整理在[董事長一頁](owner-one-page.zh-TW.md)。人從 team/README 開始讀；[TEAM.md](../TEAM.md) 是給 agent 的啟動檔。以下全部使用通用職稱，逐人導入筆記只放本機 `team/local/playbook.local.md`（不入庫）。

### 2. 4 週 pilot：1 週模擬預演 + 3 週測試工作區（看人的準備度，不看技術）

選職位的準則：主管本人願意擔任 owner；已有可以掛上去的固定儀式（早會、NCR 會議）；資料已數位化；只碰 T1 以下資料（必要時在來源端先用 `team/tools/deid.py` 去識別；它只掃通用樣式與本機 denylist，輸出要人工抽查）；能力以強化既有優勢（`strengthen`）／創造新能力（`create`）為主；實際做事的人已訪談。任一項不成立就順延。

**pilot 合計 4 週，這就是董事長核准的期間**（spec §13.2）：第 1 週模擬預演、第 2–4 週測試工作區、第 4 週五決策。到期即停；延長或擴大都要重新簽「pilot 核准」與「預算核准」。

| 波次 | 內容 |
| ---- | ---- |
| Wave 0：模擬預演（第 1 週） | 只用 mock adapter 的內建 demo（回覆為預錄）與合成資料，加上 `/team ask` 預覽（不經 gateway、無稽核，只放合成或已去識別資料）。目的：讓主管看到口吻、`🧭` 決策點與頁尾。同週 IT 部署測試工作區並演練停機一次。週五決定要不要進測試工作區。逐日做法見下方「4 週逐日表」 |
| Wave 1：測試工作區（第 2–4 週） | **生產部主管分身** + **品保部主管分身**（範例選擇；請依人的準備度換成貴公司自己的兩個職位）；分級 T1、autonomy 上限 `draft`；外包既有工作維持休眠（除非董事長在原則第 1 條勾選可啟用）。生產部：主管先貼 3 個今日重點，分身用排程資料挑戰並補漏。品保部：人先判嚴重度、先寫 8D 的 D2/D4，分身補相似案、反例與 5-why 缺口 |
| 第 4 週五 | 決策會：依下方「第 4 週決策表」決定繼續、延長或停止 |
| Wave 1b | **技術部主管分身**（ECN 影響面交叉檢查，創造新能力 `create`）— 不在這 4 週內，要另簽；只有 G2 與 G5 通過（ECN 表單與 BOM where-used 已數位化）才開；沒通過就先做流程修正 |
| 之後 | 其他部門（例：加工、業務）若閘門判 `use-command` 或 `process-fix`，就照結果走；T3（受管制或客戶要求保密的專案）等條件成熟再說（alpha 不導入）；最高負責人本人的職位不開分身，改收月彙總 |

**第 4 週決策表**（門檻由董事長在「pilot 核准」時填；導入負責人每週用下方「每週記錄表」記，系統不自動收集）：

| 看什麼 | 怎麼量 | 繼續的門檻 |
| ------ | ------ | ---------- |
| 越界次數：T2／T3 進分身頻道、分身寫入或對外發送、有人被拿分身紀錄評比 | 事件報告（原則第 9 條）＋稽核紀錄 | 預期 0；容許 ____ 次 |
| 兩位主管仍每週 review | 每週記錄表 | 第 2–4 週每週都是「是」：是／否 |
| 人改了分身結論的次數（0 代表照單全收，不是好事） | 每週記錄表的 🧭 修改數 | 3 週合計至少 ____ 次 |
| 同仁匿名問卷（第 4 週紙本 3 題）：① 分身上線後，你覺得自己的工作被取代了嗎？② 該你判斷的事，你還親手做嗎？③ 你敢在頻道說「我不同意」嗎？ | 匿名紙本；部門少於 5 人只看全公司合計 | ① 答「是」不超過 ____ 人 |

規則：全部達標 → **繼續**（另簽下一期範圍與預算）；越界超過容許，或任一位主管停止每週 review → **停止**；其餘 → **延長** ____ 週（重新簽核）。

**不看省下多少時間**：原則第 7 條。閘門 G1 的「每週幾小時」與第 1 週記下的現況（baseline）只用來決定值不值得開、開多大，**只當參考，不是成效基線**；把省時當指標，其實是外包既有工作的指標，會把分身推向取代人。人先寫 D4 的比例可以照記，當作討論材料，不列入決策。

### 3. 技能保留做法

目的：用了分身之後，人的判斷力不退化。

| 做法 | 預設 |
| ---- | ---- |
| 決策點（`🧭 需要你判斷`）：分身遇到決策點就停下，列選項與取捨，不替人選 | **預設開** |
| Show-your-work：每則實質回覆附依據、`[ASSUMED]` 假設、未查證項目、信心（只有「中」或「低」） | **預設開** |
| Predict-first（「我先說」）：分身先問人的判斷，人回答後才揭露分析並對照差異 | opt-in，每人自選，僅限標示 `predictFirstEligible` 的能力 |
| Teach-back 與人工練習 | 對已 opt-in 的外包既有工作（`outsource`）要求（teach-back 每月 1 次，另加人工練習）；其餘由個人選擇。**自報制**：沒有程式提醒、記錄或驗證，由在職者在週 review 自己說 |
| 複審節奏 | 週：在職者 15 分鐘（看錯誤回答與 `🧭` 修改率）；月：部門主管 + 導入負責人看分類分布；季：重跑閘門 |

隱私與防監控：技能保留紀錄與分身使用指標**不作為人力或績效依據**；個人資料只有本人看得到，主管只看彙總；簡報與提醒的粒度到工單或部門，不到個人。

### 4. 三分類檢查（AI 導入負責人逐一與各部門主管跑）

對每項擬開的能力，與該部門主管（職稱即可，不記姓名）逐題確認；**問實際在做事的人，不只問主管**：

1. **今天誰在做這件事？**（填 `today`；常是下屬，例如生管、品保工程師，不是分身的在職者）
2. **上線後，那個人還親手做什麼？**（填 `humanStillDoes`；若答案只剩「審閱 / 確認 / 核准 / 蓋章」，就不是強化既有優勢（`strengthen`））
3. **分類**：人仍親手判斷、分身讓他看更多 → 強化既有優勢（`strengthen`）；以前沒人做 → 創造新能力（`create`）；今天有人在做、上線後他不再做 → 外包既有工作（`outsource`）。**有爭議一律判外包既有工作。**
4. 若是外包既有工作：預設休眠。要喚醒必須在 roster opt-in，每分身最多 1 項、上限 `draft`、90 天內複審、要求 teach-back 與人工練習（自報）；核准人必須在該部門升級梯上、且不是本人。
5. 這個分身是否至少有一項強化既有優勢或創造新能力？沒有就不開。
6. 資料分級：涉及的資料最高是哪一級？T1 以下才能進 Slack / Discord；T2 只能在本機 mock；T3 不處理（設定層拒載、字樣層擋下並提示，**不是內容理解**，所以要由人自己把 T3 擋在分身頻道之外）。拿不準就往上一級。T0–T3 的白話定義與車間例子見 [team/README.zh-TW.md](../team/README.zh-TW.md)。

### 5. 資料餵入（`MFG_TEAM_DATA_T1`）：分身怎麼讀到排程／NCR

測試工作區（第 2–4 週）的價值依賴分身讀得到資料。做法是**一個資料夾，由人匯出，分身只讀**（完整表格見 [team/README.zh-TW.md](../team/README.zh-TW.md) 的「資料餵入」）：

- **放哪**：一個已存在的資料夾，路徑設在環境變數 `MFG_TEAM_DATA_T1`（建議絕對路徑、放在 repo 外、不 commit）。沒設就沒有資料。只在 `--driver claude-code` 時交給模型（唯讀：`Read`／`Grep`／`Glob`）；mock demo 的預錄回覆完全不讀它。
- **誰匯出**：該部門的資料窗口在來源端匯出（生管匯排程、品保工程師匯 NCR）；分身不連 MES／ERP、不寫回。導入負責人不是匯出者，也不保管金鑰。
- **放什麼**：只放 T1 以下：排程摘要（工單號、機台、交期餘裕、保養時段）、已去識別的 NCR（客戶 `CUST-xx`、無人名與聯絡方式）。圖紙、BOM、報價、客戶名、人名、電話、email 一律不放。
- **先去識別**：放進資料夾前，先跑 `team/tools/deid.py`（指令見 `team/local/README.md`）；有殘留命中就失敗、不寫輸出。但它只掃通用樣式與 `team/local/names.denylist`，英文客戶別名與圖號沒進 denylist 就掃不到，**匯出者每次都要抽查**。
- **格式與頻率**：沒有固定 schema；建議 UTF-8 CSV、欄名人看得懂、檔內有 `snapshot_date`。更新頻率由人決定，建議早會前（早於排程貼文）覆蓋同一檔。
- **範圍**：資料夾對該 gateway 服務的**所有分身與頻道**可見；要分開就用不同的 gateway 與資料夾。
- **驗證**：`python3 -m chat_gateway self-check --driver claude-code`（環境要有 `MFG_TEAM_DAILY_BUDGET_USD`）檢查資料夾存在；再問一個答案只在檔案裡的問題，用 `grep` 對照回覆的依據。

### 6. 這套檢查擋得住什麼（誠實版）

- **`teamctl check`（lint）檢查結構，不檢查真偽。** 能擋「沒標分類」「強化既有優勢（`strengthen`）的 `humanStillDoes` 只剩審閱」「外包既有工作（`outsource`）超過 1 項」；擋不了「標錯」（外包既有工作 `outsource` 被標成強化既有優勢 `strengthen`）或 `today` 寫「無」。真偽靠季審。
- **Teach-back 是自報**：`manualRepsPerMonth` 只驗證為 ≥ 1 的整數；沒有提醒、記錄或驗證。
- **`reviewBy`（90 天複審）到期由 lint 發現，不是執行期強制**：只有人跑 `teamctl check` 才看得到（本機 roster 過期是錯誤，CI 只警告，且 CI 看不到本機 roster）；gateway 執行期不看 `reviewBy`。請把「每月跑一次 `teamctl check`」排進週 review。
- **每分身在 `roster.json` 的項目上限 600 B** 對本機 roster 是警告 `W008`；只有 CI 檢查出貨的範例 roster 才是錯誤 `E050`。
- **程式真正強制的**：決策點 🧭 與信心只有「中／低」（gateway 的 formatter）、工具恆為唯讀、外包既有工作 ≤ `draft`、T3 頻道或分身拒載、核准只認按鈕點擊。
- **只靠 prompt 或人**：「人先寫 D4」「我先說」、分類標得對不對、第 4 週決策表的數字（手工記）。

### 稽核錨點是什麼

gateway 把每個事件記成一條雜湊鏈（只存雜湊，不存訊息文字），並自動維護一個簽章過的**檢查點檔** `audit/checkpoint.json`（預設在 `~/.local/state/manufacturing-skill/team/`，可用 `MFG_TEAM_STATE_DIR` 改；內容是每個分級的紀錄筆數、最後序號與最後一筆的 MAC）。「稽核錨點」就是這個檔、或 `audit-verify` 印出的 `head`，**另存在別處的複本**。為什麼要有：檢查點抓得到紀錄被改、刪、重排、截斷，但抓不到「日誌與檢查點被一起回退到舊版」；只有存在另一處的舊複本能抓到。

**信任模型（誠實版）**：簽章與驗證用同一把對稱金鑰（`MFG_TEAM_AUDIT_HMAC_KEY`），所以**能跑 `audit-verify` 的人也能偽造整條鏈與檢查點**。驗證只防「沒有金鑰的人」，防不了金鑰持有人。因此分工是：**金鑰保管人**在主機上跑驗證並印出 `head`；**簽收人不持金鑰**，只拿印出的 `head` 去比對另存的複本並簽名。若簽收人一定要自己跑驗證，就另給他一份金鑰複本、由不同的人保管；那份複本仍是完整的簽章金鑰（沒有「只能驗證」的金鑰），只是縮小持有人範圍，限制依然存在，請接受並寫進風險紀錄。

小廠最小分工（至少 3 人）：① AI 導入負責人（不持金鑰、不核准、不簽收）；② 金鑰保管人（IT 或管理部；持金鑰、跑驗證、複製檢查點）；③ 簽收人（最高負責人或部門主管；不持金鑰、比對 `head`、簽名）。alpha 沒有可核准的動作，核准人可暫由③兼任；金鑰保管人與簽收人不可同一人。

每週做法：

1. **金鑰保管人**設好 `MFG_TEAM_AUDIT_HMAC_KEY`，跑 `python3 team/tools/teamctl.py audit-verify <MFG_TEAM_STATE_DIR>/audit`，要看到 `audit verify: OK`，並印出各分級 `head`。
2. 金鑰保管人把 `checkpoint.json`（或印出的各分級 `head`）複製到另一台主機或唯讀儲存。
3. **簽收人**拿印出的 `head` 與另存複本比對，一致就在記錄上簽名與日期。
4. 保存期限由公司自己訂，本 repo 未訂；也請寫明：日誌沒有訊息內容，出事時要還原「誰問了什麼」得靠 Slack／Discord 與雲端平台端的紀錄。

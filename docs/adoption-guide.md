# Adoption Guide — 給 AI 導入顧問的實戰 Playbook

> 給「拿這個 plugin 去客戶端導入」的人看。
> 包括 Jason 自己對外當顧問時用的 SOP。

---

## 適用對象

- 製造業內部 IT / AI 專案負責人
- 外部 AI 導入 SI / 顧問
- 製造業老闆 / 接班人想自己導入

---

## 標準導入順序（建議 6 週）

```
W0 (週 0)：先決定要不要做
  ├─ 跑 self-assessment（下方）
  └─ 老闆 + IT 主管 alignment

W1：硬體 + 環境
  ├─ 採購 GB10（or 替代硬體）
  ├─ Ubuntu / DGX OS 裝好
  ├─ 裝 Ollama + 下載模型
  └─ 裝 Claude Code（如還沒有）

W2：plugin 安裝 + smoke test
  ├─ git clone + bash install.sh
  ├─ 測 /quote /order-status 是否有反應
  ├─ 跑 examples/ 的 demo
  └─ 業助 / 廠長 各 1 人用 1 天

W3：profile 客製
  ├─ 找 1-2 個跟 CNC profile 不太一樣的地方（材料庫、機台、流程）
  ├─ 開 profile fork：profiles/<your-company>-cnc/
  ├─ 改 agents 內的 prompt（公司術語、客戶名）
  └─ 改 know-how 內的 SOP（公司專屬）

W4：MCP 接資料
  ├─ scheduler-mcp 接你的 MES / 排程系統
  ├─ erp-connector 接你的 ERP（最花時間，常 1-2 週）
  └─ 把 mock data 換成真資料

W5：使用者試跑
  ├─ 業助試報價（同時人工跑一次對照）
  ├─ 廠長查狀態（驗證 scheduler MCP 對得上）
  ├─ 品管試 /inspect（驗證 IATF 規範對齊）
  └─ 收集回饋、調 prompt

W6：上線 + 文件
  ├─ explainer 圖卡印 A3 掛到對應部門
  ├─ 培訓 30 分鐘（每個部門）
  ├─ 第一個月密集 review，每週調整
  └─ 設置 office hour（IT 答疑）
```

## W0 Self-Assessment（評估能不能做 / 該不該做）

### Pre-flight checklist

- [ ] **公司有 Claude Code 帳號 OR 有預算買** — plugin 是 Claude Code plugin
- [ ] **IT 部門能配合** — 至少 1 人懂 bash、能裝 Ubuntu 軟體
- [ ] **有 ERP / MES** — 不然 agent 沒資料可查；如果完全沒有，先做地端「假 ERP」用 SQLite
- [ ] **流程已經數位化** — 報價、工單、檢驗都還在紙本？先做基本數位化
- [ ] **老闆理解這是輔助、不是取代人** — 預期管理對齊
- [ ] **有 1-2 個願意試的「種子使用者」** — 通常是 30-40 歲、會用智慧型手機、願意給回饋的業助 / 工程師

### Red flags（不適合導入）

- ❌ 老闆覺得「裝了就裁員」 → 內部反彈會讓你失敗
- ❌ IT 部門完全外包、自己沒人 → 維運接不住
- ❌ 完全紙本流程 → 應該先做數位轉型再來導 AI
- ❌ 客戶完全不在乎稽核 / 文件 → AI 帶來的合規優勢無從發揮
- ❌ 預算 < NT$50K → 連 GB10 都買不起，建議先用雲端 + 非敏感資料試跑

## W3 客製化 — 最常見的 5 個改動

導入時 90% 客戶會要求改這 5 個地方：

### 1. 公司術語

`core/agents/*.md` 內把「機台」改成你工廠的稱呼（如「車台」、「銑台」）。

### 2. 客戶分級

`erp-connector` 接到客戶分級後，調整 `quote-specialist` 的利潤率邏輯。

### 3. 機台費率

`infra/mock-data/machine_loads.json` 內的費率換成你工廠真實數字。

### 4. 標準件庫

如果有公司專用的標準件庫（夾治具、刀具、模治具），加到 `know-how/<company>-standard-parts.md`。

### 5. 報價單版面

`examples/sample-quote-output.md` 改成你公司的版面（含公司 logo、條款、銀行資訊）。

## 常見踩雷與對策

| 雷                 | 為什麼會踩              | 對策                                           |
| ------------------ | ----------------------- | ---------------------------------------------- |
| ERP 接得超慢       | 多半是 ERP 廠商不開 API | 先用 DB 直連 read-only replica                 |
| Agent 答非所問     | prompt 沒對齊公司情境   | W3 客製要花夠時間                              |
| 業助不用           | 沒人教 + 沒立刻可見好處 | 找個「立刻省 30 分鐘」的場景示範               |
| 客戶稽核問 AI      | 沒準備好說明文件        | 拿 explainer 02-IT部門系統說明.html 給稽核員看 |
| 老闆要看 ROI       | 沒設 baseline           | W0 就量「現在報價要多少時間」存證              |
| GB10 過熱          | 機房沒空調              | 移到有空調的辦公室                             |
| Ollama 模型答得爛  | 模型太小                | 升級到 32b 或 70b                              |
| 圖紙 PDF 解析爛    | LLM 對 CAD 弱           | 先轉 PNG / SVG，多模態模型較強                 |
| 試切結果沒回寫     | 流程斷掉                | hook 自動觸發回寫 know-how                     |
| 多人改 prompt 衝突 | 沒走版控                | profile 走 git，PR review                      |

## 導入分身團隊的順序（v0.2.0-alpha，實驗性）

> 這一節只談「虛實整合團隊」（每個職位一個副駕分身）。前面 W0–W6 先走完，再開始這一段；分身不是 W1–W6 的前置條件。入口文件：[TEAM.md](../TEAM.md)；給人讀的 10 分鐘說明：[team/README.zh-TW.md](../team/README.zh-TW.md)。以下全部使用通用職稱，逐人導入筆記只放本機 `team/local/playbook.local.md`（不入庫）。

### 1. 先過「需要分身嗎？」閘門

每個想開分身的職位，先走 [team/gate/need-a-twin.md](../team/gate/need-a-twin.md)（Claude Code 內可用 `/team gate <position>` 逐題引導）：

| # | 問題 | 不通過 → |
| - | ---- | -------- |
| G1 | 痛點每週耗幾小時？（要說得出數字） | `defer` |
| G2 | 根因是表單、權責、流程斷點，或資料尚未數位化？ | `process-fix` |
| G3 | 偶爾用一次既有 `/command` 就能解決？ | `use-command` |
| G4 | 在職者願意每週花 15 分鐘 review？ | `defer` |
| G5 | 需要的資料都可讀（已數位化、可匯出）？ | `defer` |
| G6 | 實際在做事的人（常是下屬）已訪談、`today` 已填？ | `defer` |
| G7 | 涉及 T3（高安規客製專案）？ | alpha 不開 |

全部通過才填 `result: twin`；每季複審一次，可判 `retire`。**流程修正能解決的，就不開分身** — 閘門判 `process-fix` 本身就是成果，不是失敗。

### 2. Wave 1 原型 pilot（看人的準備度，不看技術）

選職位的準則：主管本人願意擔任 owner；已有可以掛上去的固定儀式（早會、NCR 會議）；資料已數位化；只碰 T1 以下資料（必要時在來源端先用 `team/tools/deid.py` 去識別）；能力以 `strengthen` / `create` 為主；實際做事的人已訪談。任一項不成立就順延。

| 波次 | 內容 |
| ---- | ---- |
| Wave 0（2 週） | 只用 mock adapter 與合成資料重播，加上 `/team ask` 預覽。目的：讓主管看到口吻、`🧭` 決策點與頁尾 |
| Wave 1（6 週） | **生產部主管分身** + **品保部主管分身**；分級 T1、autonomy 上限 `draft`。生產部：主管先貼 3 個今日重點，分身用排程資料挑戰並補漏。品保部：人先判嚴重度、先寫 8D 的 D2/D4，分身補相似案、反例與 5-why 缺口 |
| Wave 1b | **技術部主管分身**（ECN 影響面交叉檢查，`create`）— 只有 G2 與 G5 通過（ECN 表單與 BOM where-used 已數位化）才開；沒通過就先做流程修正 |
| 之後 | 加工部、業務部多半會判 `use-command` 或 `process-fix`；高安規專案等 T3 條件成熟（alpha 不導入）；董事長室不開分身，改收月彙總 |

成功指標：人修改 `🧭` 結論的比例（大於 0 是健康的）、人先寫 D4 的比例、週 review 出席率。**不要用「省下多少時間」當指標** — 那其實是外包指標，會把分身推向取代人。

### 3. 技能保留做法

目的：用了分身之後，人的判斷力不退化。

| 做法 | 預設 |
| ---- | ---- |
| 決策點（`🧭 需要你判斷`）：分身遇到決策點就停下，列選項與取捨，不替人選 | **預設開** |
| Show-your-work：每則實質回覆附依據、`[ASSUMED]` 假設、未查證項目、信心（只有「中」或「低」） | **預設開** |
| Predict-first（「我先說」）：分身先問人的判斷，人回答後才揭露分析並對照差異 | opt-in，每人自選，僅限標示 `predictFirstEligible` 的能力 |
| Teach-back 與人工練習 | 對已 opt-in 的 `outsource` 強制（teach-back 每月 1 次）；其餘由個人選擇 |
| 複審節奏 | 週：在職者 15 分鐘（看錯誤回答與 `🧭` 修改率）；月：部門主管 + 導入負責人看分類分布；季：重跑閘門 |

隱私與防監控：技能保留紀錄與分身使用指標**不作為人力或績效依據**；個人資料只有本人看得到，主管只看彙總；簡報與提醒的粒度到工單或部門，不到個人。

### 4. 三分類檢查（AI 導入負責人逐一與各部門主管跑）

對每項擬開的能力，與該部門主管（職稱即可，不記姓名）逐題確認；**問實際在做事的人，不只問主管**：

1. **今天誰在做這件事？**（填 `today`；常是下屬，例如生管、品保工程師，不是分身的在職者）
2. **上線後，那個人還親手做什麼？**（填 `humanStillDoes`；若答案只剩「審閱 / 確認 / 核准 / 蓋章」，就不是 `strengthen`）
3. **分類**：人仍親手判斷、分身讓他看更多 → `strengthen`；以前沒人做 → `create`；今天有人在做、上線後他不再做 → `outsource`。**有爭議一律判 `outsource`。**
4. 若是 `outsource`：預設休眠。要喚醒必須在 roster opt-in，每分身最多 1 項、上限 `draft`、90 天內複審、強制 teach-back 與人工練習；核准人必須在該部門升級梯上、且不是本人。
5. 這個分身是否至少有一項 `strengthen` 或 `create`？沒有就不開。
6. 資料分級：涉及的資料最高是哪一級？T1 以下才能進 Slack / Discord；T2 只能在本機 mock；T3 不在 alpha 範圍。拿不準就往上一級。

與各對象的下一步（通用職稱）：

| 對象 | 下一步 | 產出 |
| ---- | ------ | ---- |
| 董事長室 | 20 分鐘說明「副駕不是替身」與三分類；簽署「AI 賦能原則」（分身指標與技能保留紀錄不作為人力或績效依據）；核准 pilot 範圍；指定稽核錨點簽收人 | 一頁原則、pilot 範圍 |
| 生產部主管 | 旁聽早會、記錄現行簡報形式；跑閘門；訪談生管；確認決策點；約定每週 15 分鐘 review | 閘門紀錄、baseline |
| 品保部主管 | 挑歷史 NCR 去識別後做 mock 重播；訪談品保工程師；列出 decisionRights；決定哪些能力開放「我先說」 | 合成重播劇本、閘門紀錄 |
| 技術部主管 | 盤點 ECN 表單與 BOM where-used；跑閘門；沒通過就提出流程修正案 | ECN 流程圖、閘門紀錄 |
| 加工部主管、業務部主管 | 先試用既有指令（`/inspect`、`/quote`）；收集最常重複被問的問題；跑閘門 | 試用回饋 |
| 管理部主管（IT／人資） | 決定平台（沿用既有；沒有就先用 mock）；用服務帳號建 bot、憑證只放環境變數；安裝 pre-commit 名單 hook | 部署檢核表 |

**職責分離**：AI 導入負責人不擔任核准人，也不保管稽核錨點。**現況提醒**：Slack / Discord adapter 與 Claude Code driver 尚未在 CI 對真實平台測試，需要憑證；wave 1 之前先在測試工作區驗證，並由導入負責人以外的人每週簽收稽核雜湊。

## 顧問不該承諾的事

- ❌ 「裝了 AI 就不用人」 — 永遠不會
- ❌ 「100% 準確」 — LLM 永遠有錯，要設計人類審核點
- ❌ 「3 個月回本」 — 不可能，6-12 個月正常
- ❌ 「跨領域萬能」 — 我們只懂機械加工 + 通用流程
